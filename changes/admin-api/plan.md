# Add the read-only analyst API

## Summary

Deliver stage 5 and every read in F-39 on the current Oracle schema, including card declines from stage 4. Add internal analyst seeding, analyst login, a read-only bearer scope, and an OpenAPI document for the later admin UI. Stage 7 owns screens and CSV export. Stage 8 owns deployment and Cloudflare Access verification. Keep the existing deployment configuration unchanged. Any deployment of the admin endpoints requires the Cloudflare Access protection specified by the baseline.

## Order of work

1. **Add analysts and isolate their authentication** (`bank/migrations/0021_admin_api.sql`, migration registry, admin, shared auth and outcome, routes, both OpenAPI files, event registry, `bank/tests/admin.rs` and supporting SQL).
   - Add an ANALYST table with generated internal numeric ID, stable unique analyst identifier, display name and Argon2id password hash. Add `POST /internal/v1/seed/analysts` as a bounded validated batch on the generator listener. Reuse internal seed conventions, hash before DB writes and make duplicates reject the batch atomically. Never return seed credentials or log any credential.
   - Add `POST /admin/v1/login` to the public route set. Reuse the shared bounded password verification and opaque token helpers. Check unknown accounts with a dummy Argon2id hash, use one generic 401 for unknown analyst and wrong password, and return an opaque token with `analyst:read` scope and a fixed 30-minute expiry using server wall time so a frozen or advanced simulation cannot change a human credential's lifetime. Bind the application server wall timestamp for both issuance and verification, using the same representation as ACCESS_TOKEN.expires_at. Continue to use business time for viewed data and audit occurrence. Store only the token hash in ACCESS_TOKEN with subject type ANALYST and a null customer-session ID. Check exact subject and scope, analyst existence, expiry and revocation on every read. Customer and client validators continue to require their own subject types. No sliding expiry or customer-device tracking for analysts.
   - Use channel ADMIN and distinct `analyst.login.succeeded` and `analyst.login.failed` events. Commit the analyst login event and exactly one `request.completed` together for both accepted and refused credentials. Include token issuance in the success transaction and rely on the recorder's completion-committed signal to suppress the middleware duplicate. An audit insert failure on either path returns a retryable error. Failure audit records carry no password, hash, bearer, or submitted identifier for unknown users. Generic completion covers malformed input and read requests. An audit insert failure prevents issuing a usable token. Keep read handlers free of domain writes, with the existing completion/outbox audit as the only normal read-side write.
   - Proof: `scripts/dev/it-oracle.sh migrations` verifies fresh schema and registry order. `scripts/dev/it-oracle.sh admin` checks seed isolation, batch rollback, hash-only storage, matching unknown/wrong credentials, and independent expiry and revocation. In an isolated fixture with simulation time behind wall time, check that the stored expiry falls between the server wall timestamps bracketing login plus 30 minutes. Advance simulation past that expiry and require the same bearer to work in a GET. Then backdate the stored expiry behind current wall time and require rejection. Verify revocation using a separate unexpired bearer.
   - Inject a targeted failure on the transactional `request.completed` insert after the login event insert for both correct and wrong credentials, allowing a fallback 503 completion. Always remove the fault before assertions. Require 503, no committed analyst login event, no new token row and exactly one fallback completion per request. On the normal success and refusal paths require the matching analyst login event and exactly one completion. Use an otherwise valid request to assert denial on each of customer money movement, ATM, card, and inbound deposit with an analyst bearer. On the same analyst GET, require a positive control and independently deny an ANALYST token with the wrong scope and a CUSTOMER or CLIENT token with exactly `analyst:read`. Also deny missing, customer, and client tokens. Inspect committed login, malformed and read outbox events on both routers, including searches by distinctive query values and profiles with distinctive path values. Assert one completion per normal HTTP arrival, route template or safe operation label, and no submitted identifiers, query values, bodies, or secrets anywhere in the complete correlated event records. Use distinct request IDs on the two routers. The seed path remains under the existing internal audit exclusion.

2. **Expose customer and account views** (admin feature SQL/routes, admin OpenAPI and admin tests).
   - Use these authenticated GET endpoints:
     - `/admin/v1/customers` takes exactly one of `name`, `phone`, `customer_no`. Use case-sensitive literal prefix matching with escaped SQL wildcards and the (name, customer_id) index. Reject empty or blank values for all three search fields. Use exact indexed matches for phone and customer number. Return stable, paginated results.
     - `/admin/v1/customers/{customer_no}` returns the profile. `/admin/v1/customers/{customer_no}/{collection}` supports only the explicit read routes `accounts`, `cards`, `deposits`, `loans`, `payees`, `devices`, `sessions`, `login-attempts`. Include account balances and product or card status. Order sessions by (started_at, session_id) descending and login attempts by (occurred_at, attempt_id) descending. Bind both the customer's phone and actual customer ID for attempts. The current customer login path populates customer ID for known credentials on success, wrong password and lockout, and uses null for unresolved identities. Exclude unmatched or null IDs so unaffiliated attempts cannot be attributed later. The current application has no phone-change flow. Revisit the lookup if one is introduced. Expose relevant IDs and business times with allowlisted fields. Exclude credentials, token hashes, CI hashes, reset and PIN data, and raw stored response JSON. Serve only synthetic application data.
   - Use bound SQL and numeric IDs internally. Every collection accepts an integer limit of 1–100, default 25, and fetches one extra row to signal continuation. Encode the continuation from the last returned row. Use 400 for invalid limits or malformed or mismatched cursors. Tie each cursor to its collection, parent and normalized filters. Sort name results by (name, customer_id) ascending, use the described recency keys for time-based collections, and use their unique table keys ascending for the remaining lookups. Keep all Oracle timestamp precision in cursors. Use expanded strict keyset predicates with the parent restriction and a leading-column bound, for example `parent_id = :parent AND occurred_at <= :page_time AND (occurred_at < :page_time OR (occurred_at = :page_time AND id < :page_id))`. Return 404 for a missing parent and an empty collection for an existing parent with no rows.
   - Proof: `scripts/dev/it-oracle.sh admin` validates all collection schemas, search by all three fields, duplicate names, literal LIKE metacharacters, page boundaries and cross-parent, cross-filter and cross-collection cursor rejection. With limit 1, traverse three tied rows in order with no duplicates and no cursor on the last page. Test that known-customer successes and failures appear, while null or different customer IDs using the same phone are excluded. Also check the empty/missing distinction and private authentication field exclusions.

3. **Expose ledger, card, ATM and close views** (admin feature SQL/routes, admin OpenAPI and tests).
   - `GET /admin/v1/accounts/{account_no}/transactions` filters inclusively by KST business date, channel, direction, and inclusive bounds on absolute amount. Use debit for negative ledger amounts and credit for positive ones. Bind a half-open business-date window from the first KST day through the start of the day after the last, and use (business_date, account_sequence) descending. Parse nonnegative integer amount bounds and return 400 for invalid or reversed date/amount ranges. Use decimal strings across endpoints for monetary amounts, balances, numeric Oracle identifiers and exact coordinates.
   - `GET /admin/v1/transfers/{transfer_id}` returns the transfer, every ledger leg ordered by numeric transaction ID and a safe projection of the original TRANSACTION_REQUEST outcome and codes. `GET /admin/v1/transactions/{tran_id}/terminal` joins an ATM ledger row to its terminal and exposes region and coordinates. Return 400 for malformed numeric IDs and 404 for non-ATM rows or missing terminals.
   - `GET /admin/v1/accounts/{account_no}/card-payments` joins account cards to CARD_AUTHORIZATION and its owning TRANSACTION_REQUEST, without requiring a ledger row. Page by (request business time, request ID) descending. Return the decision and merchant name, MCC, country, original currency and amount, converted won, entry mode and exact coordinates. An unknown-card decline has no account and does not appear under an account. Never expose the raw replay document.
   - `GET /admin/v1/daily-close` takes an exact business date and optional account number. Return stored balances, verification state and mismatch detail, ordered by numeric account ID ascending with the date fixed. An unknown account filter returns an empty collection. Missing or invalid business date returns 400. Collection bounds also apply here. Use existing account, request, terminal and date indexes. CARD_AUTHORIZATION has a request-ID primary key and CARD_AUTHORIZATION_CARD_IX on card ID. On populated fixtures inspect first and continuation pages for ledger and card SQL, including where Oracle filters and sorts the card join. Avoid per-row DB round trips.
   - Proof: `scripts/dev/it-oracle.sh admin` validates composed transaction filters, inclusive KST date and amount boundaries, including a final-day row after midnight, tied and sub-second pagination, transfer detail and privacy, ATM coordinates, approved and known-card declined rows from real requests. Assert the known-card decline and merchant fields appear exactly once without a transfer, and a separate unknown-card decline is absent. Check and valid/mismatched close records spanning more than one page.

## Risks and mitigations

- **Privilege crossover or accidental exposure.** Verify all admin reads require the analyst token subject and scope and that the analyst bearer grants no customer, ATM, card or inbound access. Deploy the route only with the baseline's Cloudflare Access boundary. Body and query values are excluded from new audit payloads.
- **Unbounded reads and duplicate pages.** Use bounded queries and strict cursor comparisons with stable tie-breakers. Treat pages as live reads with no cross-request snapshot.
- **Missing declines or inexact money.** Join through card and request even when a transfer row is absent. Return decimal strings and test exact coordinates and won. Keep all analyst read routes detached from money-moving services.

## Rollback or recovery

Disable or revert the routes if required. Keep schema history forward-only and revoke existing ANALYST tokens before any exposure is restored. The customer ledger and durable audit history do not require data rollback.
