# Stage 6 generator scenarios — first implementation checkpoint

## Summary

Prove that the generator can produce and recover a linked synthetic B→C transfer and the receiver's ATM cash-out through the existing bank APIs. Verify F-18 replay for the transfer and F-34 labeling throughout the proof; exercise an ATM withdrawal with a stable key in a single confirmed attempt and collect scoped evidence toward acceptance criteria 5 and 10. The proof fixture uses two synthetic demand accounts with known opening balances and a fixed, valid in-bank transfer and ATM amount. It does not count toward published B/C quotas or dormant-account coverage. The brief uses only internal baseline requirements and aggregate dataset findings. No dataset rows are needed by the proof.

This packet is the sole stage 6 change. The first checkpoint was implemented and verified under its original approval. Before closing or merging the stage, extend this packet with the approved remainder covering personas, A–G, lookalikes, source-attributed calibration, manifests, and backfill/live drivers. Record unresolved C eligibility, D timing across the live window, and B/C quota counting as questions for that extension. Track ATM replay after an uncertain response as a separate proof in the extension. Stage 8 owns the full-duration and throughput acceptance run.

## Files and components that change

- `generator/saltation_gen/client/`: extend the transfer client to accept an explicit bank transaction key and timestamp while preserving the defaults used by existing callers.
- `generator/saltation_gen/truth/`: add a per-operation recovery record in the truth database and idempotent, exact-match materialization of the existing labels.
- `generator/saltation_gen/`: expose a bounded scenario driver and CLI for the proof. Reuse existing roster, session, terminal, and context helpers.
- `generator/tests/`: focused failure-path tests and a Compose harness that can discard a successful response over the real transport.
- `bank/tests/generator_bc.rs`, `bank/tests/sql/generator_bc_*.sql`, and `scripts/dev/it-oracle.sh`: add isolated cross-store proof and include it in the existing Oracle CI entry point.

## Order of work

1. Allocate a unique run ID and stable operation identity per step. Persist run inputs and one immutable record per request with its request ID, subject labels, B/C scenario instance IDs, context and exact non-secret payload. Include the bank transaction key and an explicit timestamp taken from frozen bank KST for transfer, and a distinct idempotency key for ATM withdrawal. Never persist reusable credentials or session tokens in these records or print them. Store only status and identifiers needed to resume or investigate.
2. Use a single owner per run in the proof runner. Atomically claim a run in the truth database, reject concurrent claims, and release via a conditional update matching the current owner token. Recover a stale claim only through an explicit operator action after verifying the original process has exited, with a conditional update matching the exact stale owner. Use atomic single-document writes with acknowledged, journaled writes on the existing standalone Mongo deployment. Materialize missing labels by their unique key without a multi-document transaction. Read back and compare all label fields, including scenario and instance ID, after inserts or duplicate-key errors. Stop on conflicts or incomplete verification. Send no scenario HTTP call until its full label set is verified. Seeding and clock administration are fixture setup outside this scenario flow. On the transfer store B for the sender and C for the receiver under the same request ID, with each subject's own instance ID. Label the receiver's ATM session start and withdrawal C using that same C instance. Label login at customer level by the context of the initiating subject.
3. Mark dispatch as unconfirmed durably before each mutating call. After an ambiguous transfer result, resume the same operation from its journal, using the same sender, route, original transfer request ID, key, payload and authorization scope while the frozen business time remains valid. Transfer dedup is scoped to `C:<customer_id>` and the key, with canonical request hash comparison. Identity, scope and request validation come first. Accept HTTP 200 with the success codes `A0000` and `000` as success. The replay creates no new transfer label rows. A fresh login for the same sender gets a distinct, B-labeled customer request ID. A rejection received after ambiguity keeps the transfer unresolved unless the generator can prove it reflects a stored result. The proof does not try to infer that from a generic rejection. Stop with an unresolved record when safe replay is unavailable. Unknown login, ATM session start and ATM withdrawal outcomes stop for diagnosis in this checkpoint rather than causing another submission. Advance to ATM only after transfer success has been reconciled. Persist completion, and make rerunning a completed run read the result without sending it again.
4. Add a dedicated `generator-bc` integration target and invoke it last from `all`. Use the isolated integration stack and existing test guardrails. Stop application containers before resetting the dedicated integration schema so the test starts in BACKFILL even after the earlier live tests in `all`. Start the bank, confirm frozen time, and seed two reserved synthetic customers and a registered terminal through existing APIs. Remove only those test-fixture roster entries from the isolated truth database before reseeding, as the Mongo volume outlives the Oracle schema reset. Use a new run ID. Run the harness in a generator container with a read-only bind mount of its script from `generator/tests`, overriding the entry point with the generator image's Python and using only its runtime dependencies. The test-only transport reads and discards the actual successful transfer response, flushes a credential-free fault marker and exits the first container before cleanup, leaving the durable unconfirmed operation and claim. Require the expected terminal exit and marker before authorizing recovery against that exact stale owner token. Abort if its conditional update fails. Resume in a second container against the same Mongo run with a fresh labeled login as the same sender, reading credentials from the existing synthetic fixture roster. Before replay, assert the clock is still in BACKFILL at the recorded KST instant. Capture request IDs at the harness transport boundary before dispatch in both containers, using credential-free records on stdout. Combine those records with the test fixture's known account and customer identifiers, seeded opening balances, amounts and B/C instance IDs derived from run ID and role. Pass that fixture JSON to `cargo_test generator_bc` through an explicitly forwarded environment variable. Forward `MONGO_TRUTH_URI` separately using existing test credentials alongside `MONGO_URI`. Require the named Rust proof to execute. Missing metadata or a failed driver/verifier fails the target and `all`. Make no changes to bank server code, schema, runtime database roles, or network boundaries.

## Risks and recovery

A bank success response may be lost, a Mongo write may partially materialize labels, or a request may be rejected before the bank reaches deduplication. The journal preserves uncertain operations and prevents allocating replacement IDs. An integration failure leaves the operation unresolved and preserves evidence. Reset only the isolated test fixture. Existing `run-normal` remains usable with its existing defaults. Reverting this checkpoint requires no schema rollback in Oracle or the bank.
